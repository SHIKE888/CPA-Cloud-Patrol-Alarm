## 2. 定位过程（怎么从"参数没用"走到"通路结构性问题"）

先别急着改代码，先**把事实钉死**：

### 2.1 先证明"参数是好的"
绕开 web，直接通过 `/dev/i2c-9` 写 FPGA 的原始参数寄存器：

| 设置 | 亮度（30 帧） | 波动 |
|---|---|---|
| `CAM_EXP`(SHR0)=1187 | 93 | 1 |
| `CAM_EXP`=100 | **132** | 0 |
| `CAM_EXP`=2275 | **7** | 0 |

方向正确、完全稳定 ⇒ 参数本体没问题，是**下发/诊断**环节。

### 2.2 把"骗人的计数器"拆开
`CAM_BUSY` / `CAM_WR_CNT` 完全对不上：

- 原始寄存器 A/B 能改画面，但 `CAM_WR_CNT` **恒为 2** 不动
- 写 `CAM_TRIG`（必然触发 `need_send`）：`CAM_BUSY` 起来了 → **但只高 1.0ms 就落回**

⇒ 一句话：**请求被接住了，但看门狗在真正写完之前就超时放弃了。**

### 2.3 算清楚"一轮到底要多久"
- I2C 100kHz，每次写 4 字节（器件地址 + 寄存器地址 2 字节 + 数据）≈ **385 µs**
- 参数表 7 个寄存器 ⇒ **一轮 ≈ 2.7 ms**
- 原来的看门狗 `WD_MAX = 25000`（25MHz）⇒ **1 ms** ⇒ 每轮都提前放弃 ✔ 完全吻合

### 2.4 但还有更深的两个坑
继续推演状态机 + 从 `reg_index` 的位宽/相位推断：

- `I_ae_req` 从 25MHz 域展宽后同步过来是 **24MHz 域的 1 拍脉冲**；而主表 `TS_S==0`
  每次寄存器写入只占其中 1 拍（~9240 周期里 1 拍）⇒ **命中率极低，请求基本必丢**
- 即使接住，参数相位从 `reg_index==REG_SIZE_ST(=2)` 之后才开始 ⇒ 表是错位的

## 3. 五个缺陷（四个原有 + 一个我自己引入的回归）

### 缺陷 ①：`I_ae_req` 是单拍脉冲，会被整拍漏掉
**修**：新增粘滞位 `ae_req_lat`，置位优先，等状态机回到 `TS_S==0` 再消费。
只在复位结束后消费，免得一上电那条早期请求把主初始化表打断。

### 缺陷 ②：参数相位错位 ⇒ `0x3090` 永远写不到 ⇒ 增益完全失效
**修**：收到请求**直接强制切相位**（`O_cfg_done=1`、`O_cfg_done_r=1`、`reg_index=0`），
只写那 7 个参数寄存器。用 `O_cfg_done_r` 门控，保证上电先跑完一遍主初始化表。

### 缺陷 ③：看门狗 1ms < 真实一轮 2.7ms
**修**：`WD_MAX = 20'd500000`（25MHz ⇒ 20ms），留 7 倍余量。

### 缺陷 ④：20 位曝光拆 3 字节逐个写 ⇒ 链会抓到新旧混合值
网页把曝光拆成 `CAM_EXP_L/M/H` 依次写，而 `ui_cfg` 的链**每写一个寄存器就组合取一次当前值**
⇒ 链正好跨在那 3 次写中间时，写进传感器的就是混合值。**实测复现过：设 SHR0=100 之后连续 34 秒黑屏。**

**修**：`assign o_rt_exp = busy ? held_exp : exp_calc;` —— 一轮内恒为定值；
`need_send` 改用组合值 `exp_calc` 比较，所以本轮结束后若又来了新值会**自然再补一轮**收敛。

### 缺陷 ⑤（★ 我自己引入的回归）：`REG_SIZE`/`REG_DATA` 滞后一拍
**这是今天最值钱的一个坑，务必记住。**

`REG_SIZE` / `REG_DATA` 是 `always@(posedge I_clk)` 里的**寄存器**（不是组合逻辑），
切换相位要**下一拍**才生效。而我在"触发相位切换"的**同一拍**顺手加了一句 `TS_S <= 2'd1`：

```
请求拍 N ：设置 O_cfg_done/_r=1, reg_index=0, TS_S<=1
拍 N+1  ：TS_S==1 → 采到的还是**上一拍的 REG_DATA** ⇒ reg_index=0 那一笔
          (0x3090 = GAIN_PGC_0) 被写成一笔重复的旧值, 实际从 index 1 开始
```

**症状**：曝光正常（`19.7 ↔ 145.3`）、EV 正常、压力测试全过，**只有增益干净地完全没反应** ——
`exp=1.5ms` 下 0/18/36dB 亮度全是 `41.1`，差 `0.0`。

为什么会"只坏增益"？因为曝光在 index **4/5/6**（没错位），而增益在 **0/1/2/3**，
`0x3090` 正是有效的那一个。

**修**：删掉那句 `TS_S <= 2'd1`，让状态机下一拍由
`else if((O_cfg_done&O_cfg_done_r&O_ae_cfg_done) == 1'b0) TS_S <= 2'd1;`
自然跳转 —— 那时 `REG_DATA` 已就位、总线也必空闲。

## 5. 关键技术结论

| 结论 | 说明 |
|---|---|
| 有效增益寄存器**只有 `0x3090`** | `0x3092/0x3094/0x3096` 写了也没用。实测：只写后者亮度差 `0.0` |
| 参数寄存器清单 | `0x3090/92/94/96` ← `I_ae_data`；`0x3050/51/52` ← `I_rt_exp`（20 位拆 3 字节） |
| `I_ae_req` 必须**锁存** | 24MHz 域单拍脉冲 × `TS_S==0` 只占 1/9240 拍 ⇒ 不锁存必丢 |
| 一轮下发 ≈ **2.7 ms** | 7 个寄存器 × 385 µs（I2C 100kHz，4 字节/次） |
| 看门狗下限 | 必须 ≥ 一轮真实耗时；1ms 会造成"每轮都提前放弃"的假死锁 |
| `CAM_ID`(0xD3) **硬编码 `0xA5`** | RTL 里直接写死，**不是**"参数区存在标志"。文档写错了 |
| 单次 I2C 读寄存器 ≈ 0.55 ms | 而 `CHBusy` 脉冲只有 2.7ms ⇒ 观察它必须**板上直读**，走 web 会完全看不到 |
| `POST /api/fpga` 自身要 ~33ms | `busy` 脉冲会在 POST 返回**之前**就结束 ⇒ 不能用"POST 后再轮询"的方式测 busy |

## 8. 踩坑速查

| 坑 | 一句话 |
|---|---|
| **`REG_SIZE`/`REG_DATA` 是寄存器，滞后一拍** | 切相位那一拍**绝不能**同时推 `TS_S`，否则第一笔写成旧值 |
| `I_ae_req` 单拍 | 必须粘滞锁存；`TS_S==0` 只在 9240 拍里占 1 拍 |
| 看门狗必须 ≥ 一轮耗时 | 1ms < 2.7ms ⇒ 每轮都提前放弃，表现为"永久卡死"的假象 |
| 只在写路径"稳态"下测参数 | 3 字节逐个写会制造混合值，测出看似随机的怪现象 |
| 增益要在**低曝光**下测 | 满曝光时画面饱和，增益 0↔36dB 看不出任何差异（会误判成"增益坏了"） |
| 单次 I2C 读会偶发坏读 | 读到过 `CAM_BUSY=127` 这种非法值 ⇒ 要多数表决重试 |
| 观察 `CAM_BUSY` | 必须板上直读 `/dev/i2c-9`；走 web 会因为 POST 自身 33ms 而完全看不到 2.7ms 脉冲 |
