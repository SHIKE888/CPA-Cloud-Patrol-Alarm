# 双目前端拼接方案（双 1080p 各自 60fps）— 可行性核算与实施计划

日期：2026-10-26
分支：`feature/dual-front-stitch`（从 `feature/dual-csi` @ `25e0d10` 开出）
目标：双目两路**同时** 60fps 推给 RK，共用一条 CSI-2 链路；单目只是"看哪一半"，
切换不再动时钟 mux（彻底消灭切通道卡死）。

---

## 1. 先纠正一个前提：真正的天花板不是 VTC 的 h_frame

我原来也以为"把 VTC 上限放开"就行。逐行读代码后，实际数字如下（都是代码里的事实）：

| 环节 | 现状 | 依据 |
|---|---|---|
| dbuf 读侧位宽 | **32bit = 2 像素/beat**（YUV422 16bpp） | `ui_dbuf .R_DATAWIDTH(32)`，`I_R_XSIZE = S_r_beats` |
| VTC 行有效窗口 | `S_vtc_h_active = H_ACTIVE = 1920`（单位是 **beat**，= 3840 像素） | `system_top.v` V21 参数区 |
| 1080p60 每行实际读 | 只有 960 word（1920px），DE 窗口 1920 里用掉 960 | 被 packer 反压 |
| packer 输出 | 32bit = **2 像素/word**，`WORDS_PAYLOAD = h_active>>1` | `csi2_pack_yuv422_stream.v` |
| `csi2_frame_tx` | 1 word(=2px)/byte_clk，byte_clk = 150MHz | `pll_dsi` clk1 |
| 4K25 每行 | VTC 读 1920 word = 3840px，TX 1920+200+3=2123 byte_clk=14.15µs，行周期 17.98µs | 已在板上验证 25.00fps、ECC/CRC=0 |

关键结论：**读出侧本来就是"一行 1920 word = 3840 像素"的框架**，`S_w_beats=960 / S_r_beats=1920`
这两组参数 **4K 模式已经在用**。所以 3840×1080@60 的**读出 / packer / frame_tx / D-PHY**
这一段**不需要改位宽**，只是把"一行 960 word"换成"一行 1920 word"（= 4K 的 R/W beats），
再把 VTC 的场周期按帧率调。

真正的瓶颈在**前端**：

```
RX(40bit=4px/clk) → ui_image_correction → ui_isp → preproc → preproc_post → dbuf 写(64bit=4px)
```

这一段现在跑在 `S_hs_rx_clk`（单路 1080p60 的恢复时钟）≈ **32.4MHz**，
即 4px × 32.4M = **129 Mpx/s**。双目同时 60fps 需要 **249 Mpx/s** → 必须 **≈65MHz**（2×）。

## 2. 各档位参数核算

| 量 | 单目 1080p60（现状） | **双目 3840×1080@50** | **双目 3840×1080@60** | 4K25（已板上验证） |
|---|---|---|---|---|
| `S_h_active` (px) | 1920 | 3840 | 3840 | 3840 |
| `S_v_active` | 1080 | 1080 | 1080 | 2160 |
| `W_BEATS` (64b/4px) | 480 | 960 | 960 | 960 |
| `R_BEATS` (32b/2px) | 960 | 1920 | 1920 | 1920 |
| VTC `h_active` (word) | 1920 | 1920 | 1920 | 1920 |
| VTC `h_frame` | 2200 | 2652 | 2200 | 2652 |
| VTC `v_frame` | 1125 | 1125 | 1125 | 2225 |
| 输出帧率 | 59.6 | **49.4** | **59.6** | 25.0 |
| 前端像素率 | 129 Mpx/s | 249 | 249 | 207 |
| 前端时钟(4px/clk) | 32.4MHz | ≥62.2 | ≥62.2 | 51.8 |
| `pclkx1` DE 占用 | 44% | 72% | 87% | 87% |
| TX 每行 (byte_clk@150M) | 1163 = 7.75µs | 2123 = 14.15µs | 2123 = 14.15µs | 2123 = 14.15µs |
| VTC 行周期 | 14.92µs | 17.98µs | 14.92µs | 17.98µs |
| **TX 行余量** | 48% | **21%** | **5.2%** | 21% |
| 场消隐 | 671µs | (1125-1080)×17.98 = **809µs** | 671µs | 1168µs |
| 链路载荷 (=2B/px) | 248.8 MB/s | 414.7 MB/s | 497.6 MB/s | 414.7 MB/s |
| 占 1200Mbps×4=600MB/s | 41% | 69% | **82.9%** | 69% |

三条硬结论：

1. **3840×1080@60 的载荷 497.6MB/s 与"4K30"完全相同**。历史上 4K30 被标成"99.5% 带宽、
   跑不动"，那是 **V21 把 VCO 提到 1200Mbps 之前**（当时按 500MB/s 算）的结论，**已过期**。
   现在 600MB/s 下它是 82.9%，与已验证的 4K25（69%）同一量级但更激进 → **必须板上实测**。
2. **60fps 时每行 TX 余量只有 5.2%**（行周期 14.92µs，TX 需要 14.15µs），
   而 GAP_LINE=200 是实测调好的、**不许动**。余量这么小，packer 任何一个气泡
   都会变成 MIPI CRC/ECC 报错。
3. 场消隐 671µs < 4K25 时记录过的"RK 要求 ≥1000µs"。**这条要求需要重新确认**
   （当时是 4K 场景的经验值，未必对 1080 行成立）。

→ 因此方案定为**两档，可运行时切换**：
- **D 档（先打通）：3840×1080 @ 49.4fps**，TX 余量 21%（= 已验证的 4K25 同余量），载荷 414.7MB/s。
- **E 档（再冲）：3840×1080 @ 59.6fps**，余量 5.2%，载荷 497.6MB/s。若出现 CRC/ECC → 退回 D 档。

## 3. 架构：前端拼接 + 常开双目

```
                 ┌── X_ui_image_correction (cam0) ── 40b/4px @ S_hs_clk0 ─┐
I_clk_hs_p  ── RX0 ┤                                                        ├─ dual_stitch ─ 40b/4px @ S_st_clk
I_clk1_hs_p ── RX1 ┤                                                        │      └─ 3840×1080, 带 tuser/tlast
                 └── X_ui_image_correction (cam1) ── 40b/4px @ S_hs_clk1 ─┘
                                                                                      │
                       ui_isp → preproc → preproc_post → dbuf 写(64b/4px) ────────────┘
                       dbuf 读(32b/2px @147.5MHz) → csi2_pack → csi2_frame_tx → D-PHY
```

要点：

1. **`dual_stitch` 是唯一跨时钟点**。每路各一个"整行乒乓缓冲"（486 组 × 40bit ≈ 2.4KB，
   BRAM 512×40 ×2 bank）：
   - 写侧 = 该路自己的恢复时钟（`S_hs_clk0` / `S_hs_clk1`），按 `tuser` 起行、`tlast` 或
     486 组收行；
   - 读侧 = `S_st_clk`（新时钟，见下），一行内先吐 cam0 的 486 组、再吐 cam1 的 486 组；
   - 读侧靠"整行落后一行"工作，天然吸收相位差；
   - **掉一路（没插模组 / 无 HS 时钟）→ 该半幅填黑**，整条流水线照常 3840 跑，
     不会像现在这样"mux 选到没时钟的源 → 整条链死掉"。
2. **`S_st_clk`** = `S_pclkx1`(147.5MHz) / 2 = **73.75MHz**（一个 Toggle FF + BUFG，不新增 PLL）。
   相对 62.2MHz 的硬需求留 18% 余量，用来吸收行相位抖动。
3. **`S_hs_rx_clk` 时钟 mux 彻底删除**（连同 `S_clk_sel_r`、`PH1_LOGIC_BUFG X_bufg_rx_clk`、
   `remote` 的换源复位窗保留但不再承担"换源"职责）。
   → **`rx_sel` 从"时钟 mux 选择位"降级为"网页显示哪一半"**，切通道不再触碰任何硬件时序，
   这是"杜绝卡死"最彻底的解法。
4. **单目 = 网页裁半边**（现有 web 已经在做 `drawImage(src, 0|hw, 0, hw, h)`），
   `0xDB[0]` 只影响前端 mark 标记；RK/FPGA 都按 3840×1080 出流。
5. **`dual_frame_sched` 保留但停用**（旧 1920 通路可一键回退，见 §5）。

时钟/带宽核对：

| 项 | 值 | 判断 |
|---|---|---|
| `S_st_clk` 4px/clk 吞吐 | 73.75M × 4 = **295 Mpx/s** | 需求 249 → 84%，余量够 |
| 每行读两半耗时 | 972 组 / 73.75MHz = 13.18µs | 行周期 14.8µs → 余 1.6µs |
| dbuf 写 | 64b/beat @73.75MHz = 590 MB/s 能力 | YUV422 2B/px × 249M = 498 MB/s → 84% |
| DDR 读写合计 | ≈ 498 + 498 = 996 MB/s | 4K25 是 414+414=828，**+20%**，需实测 DDR 余量 |
| ISP/preproc 时钟 | 73.75MHz（4K25 已验证 51.8MHz） | **+42%，时序风险最高的一项** |

## 4. 分阶段实施（每阶段独立可回退）

### Stage 1 — `dual_stitch.v`（纯新增，不影响现有 bit）
- 新文件 `fpga/uisrc/01_rtl/dual/dual_stitch.v`（40bit / 4px / 1024 行深双 bank + 掉路填黑）。
- 新增 `fpga/uisrc/02_sim/tb_dual_stitch.v`：
  - 两路各灌"行号+列号"可判别图案，`S_hs_clk0/1` 频率故意不同（32.4 / 32.9MHz）、相位错开；
  - 断言：输出每行 = 486 组 cam0 紧跟 486 组 cam1、行号连续不跳、`tuser` 只在第 0 行/256 行窗口出现；
  - 掉一路：断言另一半全 0。
- 验收：iverilog 全绿；`check_syscon` 不引入新的组合环。

### Stage 2 — 视前端频率（最危险的一步，先只做时钟）
- `S_hs_rx_clk` 改为 `S_st_clk`(73.75MHz)，但 **stitch 先旁路**（两路都由 `S_st_clk` 采样，
  单路照旧出 1920×1080）。目的：**单独验证 ISP/preproc/dbuf-write 在 73.75MHz 下能否收敛**。
- 验收：TD 综合报告 **所有时钟 SWNS ≥ 0**（历史上有 clk5 SWNS −6.809ns 的负余量，
  必须先清干净再谈提速）；板上单目 1080p60 仍 59.6fps、无 CRC。

### Stage 3 — 打开拼接，D 档（49.4fps）
- `dual_stitch` 接入，替换 `dual_frame_sched`；`S_res_mode` 新增 `2'd3` = "拼接 3840×1080 D 档"
  （`h_frame=2652 / v_frame=1125`）。
- 验收：`/stream` 抓帧左右两半**必须不同**（`half_meanabsdiff` 要显著 > 2；当前故障时是 1.56）；
  挡住任一摄像头，对应半边变黑而另半边正常；`v4l2-ctl --stream-count=180` 实测帧率 ≥ 49。

### Stage 4 — E 档（59.6fps）
- 只改 `h_frame=2200`（其余不变）。验收同上，帧率 ≥ 59；同时检查 `dmesg` **零** CRC/ECC。
- 若报 CRC/ECC → 保持 D 档并记录（不要动 GAP_LINE）。

### Stage 5 — RK/Web 侧
- 单目/双目只切"显示哪一半"，`/api/fpga` 的 `RX_SEL` 不再写 `0xDB[0]` 的硬件 mux 语义；
- 删掉换源复位窗里"必须切时钟"的假设；
- 抓拍 `/snapshot.jpg` 支持 `?half=0|1`。

## 5. 回退开关（必须做，否则一次烧错就废）

`0xE0` (RES_MODE) 扩成三档，**上电默认仍是现在的 1080p60 单目通路**：

| `0xE0` | 含义 | 通路 |
|---|---|---|
| 0 | 1920×1080@59.6 单目（**默认**） | 现 `dual_frame_sched` + 时钟 mux |
| 1 / 2 | 4K30 / 4K25（现状保留） | 现通路 |
| 3 | 拼接 3840×1080 D 档 49.4fps | 新 stitch |
| 4 | 拼接 3840×1080 E 档 59.6fps | 新 stitch |

模式 0/1/2 与 3/4 之间切换走现成的 500ms 复位窗；3↔4 之间只改两个计数器，不需要复位窗。

## 5.5 ⚠ 赛题要求修正（2026-10-26 用户确认）—— 本节取代上文所有"raw 推流"结论

> 赛题要求：**传给 RK 的必须是 JPEG 压缩图**，有损/无损/可变码率都要有；
> **双路 1080p60** 与 **单路 4K30** 两个指标；**RK 端软件压缩不允许**。

所以上文"链路 497.6MB/s / TX 余量 5.2% / D 档 E 档"那一整套核算**全部作废** ——
链路走 JPEG 后带宽只剩十几 MB/s，带宽不再是约束。真正的约束变成**编码器吞吐**。

### 5.5.1 两个指标其实是同一个数

| 指标 | 像素率 |
|---|---|
| 双路 1080p60 | 2 × 1920×1080×60 = **248.8 Mpx/s** |
| 单路 4K30 | 3840×2160×30 = **248.8 Mpx/s** |

→ 编码器只要做到 **≈250 Mpx/s**，两个指标**同时**达成。是一条门，不是两条。

### 5.5.2 现在这条 JPEG 支路的三处硬伤（代码事实）

| # | 问题 | 证据 |
|---|---|---|
| ① | 编码器挂在 `S_hs_rx_clk`（单路 32.4MHz）域，不是快时钟域 | `.clk(S_hs_rx_clk)` |
| ② | 312 拍/MCU；16200 MCU/帧 → 32.4MHz 下 **1080p 只有 6.4fps**；搬到 147.5MHz 才是文件头自述的 29fps | 文件头注释 |
| ③ | **`s_ready` 悬空未使用**，且只接 `S_yuv_data[31:0]`（64bit=4px，每拍丢一半像素） | `:624/:658` vs `:473` |

③ 是结构性错误：上游完全不看反压，编码器每拍只收 4 个像素里的 2 个 → 行缓冲凑不成行。
**这条支路从来没有、也不可能出过一帧正确的图。**

### 5.5.3 好消息：差的倍数没想象中大，而且不用加 DSP

设计文档已写明提速路径：让"块 i 的 DCT/量化"与"块 i−1 的熵编码"并行（加一块 64×16
双缓冲），每 MCU 从 312 拍降到 **≈150 拍**。但文档是按 147.5MHz 算的，才得出 60fps@1080p。

**而 `pll_dsi.clk3_out` 本来就有 300MHz 输出，当前无人使用。**

$$\frac{300\,\text{MHz}}{150\,\text{拍/MCU}} = 2\,\text{M MCU/s} \times 128\,\text{px/MCU} = \mathbf{256\ Mpx/s}$$

刚好覆盖 248.8 Mpx/s。**且不需要新增任何 DSP** —— 这点是决定性的：

| 最近一次综合（2026-10-25 15:36，`JPEG_EN=1`） | 占用 |
|---|---|
| slices | 43993 / 64320 = **68.4%** |
| ERAM | 164 / 272 = **60.3%** |
| **DSP** | **234 / 240 = 97.5%** ← 已满 |

DSP 只剩 6 个 → "再复制一套 DCT""两路各一个编码器实例"这类并行方案**全部不成立**。
唯一可行路线是 **提时钟 + 流水化**，而这条恰好够用。

注意 256/248.8 只有 **2.9% 余量**，太薄；实际要做到 **≤142 拍/MCU（≈270 Mpx/s，8% 余量）**。

### 5.5.4 RK 侧

- DT=0x18 (JPEG8)：rkcif 是否接受 **待验证**（`/dev/video22` 目前只上报 YUV）
- 兜底：DT=0x2E (RAW8) 承载 + 用户态按字节流解析（需补足定长帧）
- 解码：MPP 硬解 (jpegd)；更省的做法是 **MJPEG 直通**给浏览器自己解，RK 端零解码成本

## 6. 未验证 / 需要实测的点（不要当成结论）

1. **链路能否吃 497.6MB/s**：82.9% 是**推算**（600MB/s 上限来自 V21 的 1200Mbps×4），
   没有任何一次板上实测跑过 4K30。E 档能不能成，只能烧上去测。
2. **场消隐 671µs 是否满足 rkcif**：历史记录写"RK 要求 ≥1000µs"，出处待查；若不满足，
   60fps 直接不可行，最好情况是 1080 行 + 67 行消隐 = 58.4fps。
3. **73.75MHz 下 ISP/preproc 时序**：现有工程在 4K25（≈51.8MHz）能跑，+42% 后是否收敛未知，
   且历史综合报告里已有负余量路径。
4. **DDR 带宽 996MB/s**：板载 DDR 型号/位宽未核，4K25 的 828MB/s 是唯一参考点。
5. **两路传感器的行/帧相位**：靠 `sensor_sync_start` 同时 RSTn + 重跑初始化表；
   拼接是按"整行乒乓"做的，允许最多 ±1 行的偏差，超过 1 行会出现左右错行。

（注：§6 的 1/2 两条属于"raw 推流"路线，链路改走 JPEG 后已不适用，保留作历史记录。）

## 7.2 顺带必须改的一件事：模式表的"可不可行"判据

`_mk_mode()` 现在按 **未压缩链路带宽** 算 `load_mb_s` / `load_pct` / `ok`：

```python
load = w * h * fps * 2.0          # 2B/px 未压缩
"ok": (load / LINK_BYTES_PER_SEC) <= LINK_USABLE_RATIO
```

链路改走 JPEG 后这套判据**整个失效**（JPEG 只占 3% 带宽，4K30 也会显示"ok"，
但 `4k25` 同样会显示 ok，判不出谁可行）。必须改成按**编码器吞吐**判：

```python
need_mpx_s = w * h * fps / 1e6
"ok": need_mpx_s <= ENCODER_MPX_S      # 约 256，留余量取 250
```

否则删了 4K25 之后，模式表还是会给出误导性的"带宽 82.9% 可用"之类结论。

## 8. 2026-10-26 实测：编码器真实吞吐（推翻了两条旧结论）

测试台 `fpga/sim/tb_jpeg_thru.v`（`run_jpeg_thru.ps1 [0|1]`，320×256 / 640 MCU，
`clk/MCU` 与分辨率无关，帧头/drain 已被摊薄）。合成斜坡输入，`s_valid` 恒 1，
`s_ready` 真反压，`m_ready` 恒 1（只测编码器本体）。

| 模式 | clk/MCU | @300MHz | 需要多少 MHz 才能 248.8 Mpx/s |
|---|---|---|---|
| **有损**（DCT/SOF0） | **150.0** | **255.9 Mpx/s**（1080p123 / 4K30.9） | **292** |
| **无损**（DPCM/SOF3） | **320.2** | 119.9 Mpx/s（1080p58 / **4K14.5**） | **622（不可能）** |

### 结论 1：`jpeg_encoder_top.v` 文件头注释是**过期的**
注释写"312 拍/MCU、29fps、要 60fps 需做块级流水"。实测 **150 clk/MCU** ——
块级流水（`pend` / qzz 双缓冲 / 熵编码后台调度）**代码里已经实现了**。
所以原计划里的 **"J3 流水化"这一步不需要做**，直接省掉。

### 结论 2：300MHz 就够双路 1080p60 / 4K30（余量 2.7%）
$128 \text{ px/MCU} \div 150.0 \times 300\text{MHz} = 255.9$ Mpx/s，对 248.8 有 **2.7% 余量**。
余量很薄，所以**先拿 4K25（207 Mpx/s，占 81%）打通链路**，再冲 4K30。

### 结论 3：**无损路径两个新问题**（赛题要求无损，必须修）
1. 吞吐只有有损的 47%（320 clk/MCU），@300MHz 4K 只有 **14.5fps** —— 差 2.5 倍。
2. **仿真里第一帧之后就再不出第二帧**（`st_busy` 不再拉高，s_valid 一直有效也不响应）。
   疑似 `ll_run` / `ll_ready` 在帧间没有正确复位（代码里已有注释提示
   "ll_start 必须在复位里清，否则 u_ll 的 i_ready 会变 X"）。
   → 无损路径从未在板上跑过，这条要单独排。
